# 09a — Фоновая проверка и публикация импорта

## Цель

Парсер и CLI из 05 умеют проверить источники; API 06 загружает приватные объекты и сохраняет manifest. Подключить фоновую задачу Trigger.dev, которая проверяет данные и атомарно публикует неизменяемую `DatasetVersion`. Это отдельный жизненный цикл импорта, не этап `CalculationRun`.

**Статус:** запланировано, не реализовано. **Зависимости:** 05, 06, 09. До начала согласовать расширение модели 04: состояние ожидания, версия manifest, уникальность попытки и запись намерения отправки задачи.

## Контракт и состояния

- Расширить `POST /api/projects/[projectId]/imports/[importId]/finalize` из 06. Тело `{ manifest }`; сервер проверяет владельца, незакрытый проект и принадлежность **каждого** объекта manifest тому же проекту. Произвольный URL, bucket/key клиента и ссылки на чужой импорт запрещены.
- В одной транзакции заморозить manifest и его hash, записать `awaiting-validation` и намерение отправки `validate-import`. Вернуть `202 { data: { importId, status: "awaiting-validation", validationPending: true } }` только после сохранения. Сам HTTP не скачивает и не разбирает всю книгу.
- Повтор с тем же manifest/hash возвращает существующий импорт (`200`) и его реальное состояние; несовпадающий manifest для уже зафиксированной попытки — `409`. Исправление сопоставления создаёт **новую попытку импорта**, ссылающуюся на прежние закрытые объекты, а не меняет готовый набор.
- `POST /api/projects/[projectId]/imports/[importId]/attempts` из06 после проверки владельца создаёт новую попытку из прежних SourceObject и фиксирует manifest/dispatch атомарно; ответ202 и новый importId. Идемпотентность по04 действует и здесь.
- Первый finalize с unresolved mapping выполняет безопасное извлечение листов/заголовков в задаче и заканчивается needs_mapping. GET импорта06 отдаёт структурированный report для UI13; не требовать заранее готовый mapping, чтобы узнать заголовки. После новой попытки с подтверждёнными полями возможен ready.
- Состояния попытки: `uploaded → awaiting-validation → validating → ready | needs_mapping | invalid | failed`. `failed` — окончательный технический сбой; `invalid` — неприемлемые данные; `needs_mapping` — требуются явные решения о полях/единицах. `ready` означает принятый набор, не полноту M1–M4.
- Внутренний payload: `{ importId, projectId, requestedBy }`. Manifest, ключи объектов, версии схемы/адаптера и лимиты работник получает из БД, не из аргументов клиента.
- Ответ чтения импорта в 06 содержит `importId`, `status`, `stateVersion`, `datasetVersionId | null`, безопасную ошибку/сводку отчёта и timestamps. Подробный отчёт доступен только владельцу, без публикации исходных строк в сторонние сервисы.

## Реализация

1. `lib/server/imports/dispatch.ts`: создать/восстановить сохранённое намерение dispatch отдельно от расчётных запусков. Ключ внешней задачи `import:{importId}`. Использовать механизм повторной отправки 09, но разделять тип работы `import` и `calculation` и их конечные состояния.
2. `trigger/validate-import.ts`: повторно проверить существование/владельца проекта, состояние попытки, сохранённые версии и ограничения. Получать файлы только через `lib/server/storage.ts`; ограничивать распаковку, число листов/ячеек, память, время и размер партии по политике 05.
3. Проверить фактическое содержимое/контрольную сумму до парсинга или в ходе безопасного потокового чтения. Проверка из HTTP может использовать только достоверные метаданные/проверенную S3 checksum; клиентский hash и ETag без подтверждённой семантики не доказывают целостность. Если S3 не даёт нужного подтверждения, сверка bytes выполняется здесь, не внутри finalize.
4. Вызвать `validateImport(manifest, objects)` из 05. Не переписывать правила парсинга в задаче и не передавать таблицы в OpenAI. `needs_mapping`/`invalid` сохраняют диагностический отчёт и не создают видимую версию набора.
5. `commitDataset(validatedDraft)` публикует нормализованные строки, неизменяемый manifest и итоговый отчёт атомарно. При больших объёмах допустима промежуточная запись в закрытый staging с последующим атомарным указателем публикации; ни один API не читает staging как готовый набор.
6. Уникальность результата привязать к логической попытке/manifestHash/версиям адаптера и схемы, а не только к checksum файла. Один и тот же набор в одной попытке после повтора даёт тот же `datasetVersionId`; новое сопоставление может создавать новую версию из тех же bytes.
7. Отчёт в приватном S3 хранить по детерминированному ключу попытки/версии и checksum; БД ссылается только на полностью записанный объект. Сбой между записью отчёта и коммитом не создаёт вторую версию или два события принятия. Невостребованные объекты очищаются только по согласованной политике.
8. При смене состояния увеличивать `stateVersion`, записывать безопасное событие аудита. Список импортов из 06 читает БД. Liveblocks-комната расчёта 11 не используется для импортов; достаточно ограниченного опроса из интеграции 13.

## Ошибки и безопасность

- Повторять ограниченно только временные технические ошибки. Ошибки формата, контрольной суммы, анонимизации и явное требование сопоставления не повторять автоматически.
- Сбой после публикации, но до подтверждения Trigger завершается чтением сохранённого результата, не новым коммитом. Незавершённая отправка после рестарта восстанавливается из dispatch-записи.
- Уникальность БД сохраняется после истечения/сброса ключа Trigger. Не обещать однократное выполнение процесса; гарантировать отсутствие дублированного опубликованного результата.
- Архивирование/утрата доступа, обнаруженные до публикации, блокируют коммит; устаревший работник не публикует данные в закрытый проект.
- Логи содержат ID, количество строк, этап и код ошибки; не значения ячеек, клиентские ID, подписанные URL или секреты. Отчёт с чувствительными фрагментами остаётся в закрытом контуре и выдаётся после авторизации.

## Ограничения объёма

Не запускать расчёт автоматически после импорта, не создавать `CalculationRun` для проверки книги, не менять формулы 07/08, не добавлять UI или Liveblocks. Не исправлять неизвестные единицы/пустые кеши догадкой. Набор с ограниченным покрытием нельзя выдавать за полный.

## Проверка готовности

- [ ] Finalize быстро возвращает `202` после устойчивого намерения, без чтения полной книги в HTTP.
- [ ] Повтор finalize/задачи и сбои до/после dispatch, записи отчёта и коммита дают один опубликованный набор и отчёт одной попытки.
- [ ] Исправление manifest того же файла создаёт новую попытку/версию; предыдущая неизменяема.
- [ ] Проверены `ready`, `needs_mapping`, `invalid`, `failed`; ошибки/пропуски не становятся нулями.
- [ ] Поддельный payload, чужой объект в manifest, checksum mismatch и архивированный проект не проходят публикацию.
- [ ] Прерванная запись больших данных не видна как готовая версия; доступ к отчёту изолирован по владельцу.
- [ ] Выполнен smoke-тест Trigger/S3/PostgreSQL на синтетике либо явно записаны внешние блокеры; обновлён трекер.
- [ ] Проходят `npm run lint`, `npx tsc --noEmit`, `npm run build`.
