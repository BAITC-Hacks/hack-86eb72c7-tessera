# 09 — Фоновые расчёты через Trigger.dev

## Цель

После модели данных и проверенного расчётного ядра запускать воспроизводимый расчёт вне HTTP-запроса. Trigger.dev управляет выполнением этапов, PostgreSQL хранит бизнес-статус. Этот модуль не строит интерфейс и не утверждает заказ.

**Статус:** запланировано, не реализовано. **Зависимости:** 03, 04, 06, 08. API использует проверку владельца из 06; она должна быть завершена до открытия маршрутов. 10 добавляет ИИ-этап, 11 — уведомления.

## Конфигурация

Trigger.dev выбран пользователем, но не установлен. При реализации проверить текущие `@trigger.dev/sdk` и CLI, зафиксировать совместимые версии. Создать `trigger.config.ts`; `TRIGGER_SECRET_KEY` — серверный секрет, идентификатор проекта — явная настройка. Аккаунт, регион, размещение и численные лимиты времени/параллелизма/повторов требуют решения до запуска реальных данных. Не добавлять бесконечные повторы или неограниченную очередь.

## Контракт API

Общий формат JSON — из архитектуры; все ресурсы проверяются по владельцу. `401` без сессии; `404` для чужого/неизвестного ресурса; `422` для неправильных данных; `409` при конфликте; `503` при недоступной инфраструктуре.

- `POST /api/projects/[projectId]/runs`: `{ datasetVersionId, scope: { warehouseIds, categoryIds }, configuration, idempotencyKey }`. Массивы содержат только идентификаторы этой версии; пустой массив означает отсутствие ограничения по соответствующему измерению. `configuration` проходит схему 07/08; произвольные дополнительные поля отклоняются. Успех `202`: `{ data: { runId, status: "queued" } }`.
- Ключ идемпотентности ограничен пользователем/проектом и типом операции. Повтор того же ключа и тела возвращает существующий запуск с актуальным статусом (`200`); тот же ключ с другим телом — `409`. Новый намеренный расчёт требует нового ключа.
- `GET /api/projects/[projectId]/runs?cursor=...&limit=...`: `{data:{items,nextCursor}}`, только история своего проекта, стабильный порядок createdAt/id по убыванию; default50/max200. Элемент содержит ID/статус/дату/область/версию набора и признак полноты, не сырые продажи.
- `GET /api/runs/[runId]`: `{ data: { runId, projectId, datasetVersionId, status, stage, stageStates, stateVersion, scope, configuration, asOfDate, algorithmVersion, coverageGate, blockingReasons, canApprove, warnings, explanationStatus, createdAt, startedAt, finishedAt, error } }`. До первого этапа `stage: null`; ещё не наступившие времена и отсутствующая ошибка — `null`. Здесь только состояние; результаты читает следующий маршрут этой спецификации. 08 предоставляет чистый расчётный модуль, не HTTP API.
- `GET /api/runs/[runId]/recommendations?cursor=...&limit=...&supplierId=...&q=...&urgency=...`: `{ data: { items, nextCursor, supplierGroups, resultVersion } }`. `items` содержит сохранённые строки 08 с `recommendationId` и детерминированным обоснованием; после 10 — необязательный проверенный ИИ-артефакт. Устойчивый порядок `supplierId, warehouseId, productId, recommendationId`; курсор связан с запуском, фильтром и версией результата. Начальный проектный лимит 50, максимум 200; неизвестный/чужой поставщик не раскрывает чужие данные. `supplierGroups` содержит ID, русское название и число строк группы для текущего запуска, но не сумму разных единиц. Читать только полностью опубликованный результат `succeeded`, иначе `409 RESULTS_NOT_READY`; готовый пустой результат — `200` с пустым списком. `q` — ограниченный поиск по артикулу/названию, `urgency` — только enum08; фильтрация выполняется сервером до пагинации. Фильтр, курсор и лимит проверяются; принадлежность запуска владельцу обязательна до запроса строк.
- `POST /api/runs/[runId]/cancel`: возвращает `202` и актуальный снимок после принятия отмены; повтор уже отменённого запуска — `200`; после `succeeded`/`failed` — `409`. Проверки доступа обязательны независимо от наличия кнопки.

`explanationStatus`: `not_requested | pending | succeeded | degraded`; до подключения 10 — `not_requested`. Числовой успех не зависит от ИИ. `configuration.runMode=full` отклоняет отсутствие обязательных источников до расчёта; diagnostic возвращает только обоснованные данные и явные причины неполноты. `canApprove` вычисляется по04/14 сервером, не из статуса UI. Тексты безопасных ошибок и предупреждений — русские.

## Реализация

1. `lib/contracts/runs.ts`: проверяемые схемы API/внутреннего payload, перечисления статусов. `status`: `queued | running | succeeded | failed | cancelled`; `stage`: `validate | forecast | recommend | explain`; состояния этапа: `pending | running | succeeded | failed | skipped`.
2. `lib/server/runs.ts`: авторизация, проверка готовности версии, снимок области/параметров/версии алгоритма; уникальность идемпотентного запроса в БД. Транзакционно сохранять запуск и намерение отправки. Нельзя получить `202` за работу, о которой нет устойчивой записи.
3. Обработчики: `app/api/projects/[projectId]/runs/route.ts`, `app/api/runs/[runId]/route.ts`, `app/api/runs/[runId]/cancel/route.ts`, `app/api/runs/[runId]/recommendations/route.ts`. Они не обрабатывают книги, не вызывают OpenAI и не вычисляют прогноз.
4. `trigger/calculate-procurement.ts`: задача получает `{ runId, projectId, datasetVersionId, requestedBy }`, но заново сверяет связи и право инициатора по БД. Числовые настройки читает из снимка запуска, не из изменяемого проекта или непроверенного payload. Этапы: проверка → прогноз → рекомендации → объяснение. Без 10 последний этап `skipped`, с готовым шаблонным текстом.
5. Результаты записывать с уникальными ключами запуска/строки и транзакционным завершением. Не показывать частичный набор как готовый. Сохранять завершённые этапы так, чтобы повтор после сбоя не дублировал строки и аудит.
6. Отправитель и механизм восстановления незавершённых dispatch-записей переиспользуют один ключ `calculation:{runId}`. Сбой между записью БД и вызовом Trigger или после вызова до записи его ID должен восстанавливаться без нового бизнес-запуска. Конкретный механизм восстановления и его запуск документировать и тестировать; одного вызова из HTTP недостаточно.
7. `stateVersion` монотонно увеличивать при коммите смены состояния. Только после коммита необязательный адаптер 11 публикует уведомление. Сбой публикации не откатывает вычисления.

## Повторы, отмена и безопасность

- Повторять только временные сбои: сеть, допустимый rate limit, временная недоступность. Ошибочные входы, утраченный доступ, неизвестная версия алгоритма и исчерпанный бюджет — конечная ошибка, не цикл.
- Внутренние попытки остаются одним бизнес-запуском. После окончательного `failed` пользователь может создать новый запуск; старый остаётся неизменяемым для аудита.
- Отмена атомарно конкурирует с завершением: кто первым перевёл БД в конечное состояние, определяет исход. Поздняя запись от работника не переводит `cancelled` в `succeeded`. Между этапами проверять отмену; отменять также соответствующий Trigger run по серверному API выбранной версии.
- ИИ-ошибка в 10 фиксируется как `degraded`, сохраняется шаблонное обоснование, расчёт заканчивается `succeeded`. Логи содержат только ID, этапы, сроки и безопасные коды.
- Не выдавать браузеру `TRIGGER_SECRET_KEY` и не разрешать прямое создание произвольных задач клиентом. Повтор выполнения не может вызвать утверждение, экспорт или отправку.

## Ограничения объёма

Не менять формулы 07/08, не добавлять cron-перерасчёт, автономные агенты, UI, совместное редактирование, утверждение/рассылку. Правила импорта остаются в 05; отдельная спецификация 09a подключает их к инфраструктуре Trigger, не используя жизненный цикл `CalculationRun`. Изменение review, утверждение и экспорт реализуются отдельно в 14; 13 подключает только чтение/импорт/расчёт, 14a подключает действия проверки и утверждения.

## Проверка готовности

- [ ] `202` появляется после устойчивой записи; большой расчёт не удерживает HTTP-запрос.
- [ ] Повтор одинакового запроса/сбой dispatch/повтор задачи создают один бизнес-запуск и один набор результатов; другое тело с прежним ключом даёт `409`.
- [ ] Проверены все конечные состояния, лимит повторов, отмена до старта и гонка отмены с завершением.
- [ ] Чужой пользователь получает `404` на чтение, запуск и отмену; поддельный payload не обходит владельца.
- [ ] При отказе ИИ/Liveblocks числовой результат и шаблонное обоснование доступны; ошибки расчёта не маскируются.
- [ ] Перезапуск/переподключение восстанавливает состояние из БД; частичные результаты не утверждаются.
- [ ] Страницы рекомендаций стабильны и не дублируют строки; фильтр поставщика и поддельный курсор не обходят владельца; незавершённый результат даёт `409`.
- [ ] Реальный smoke-тест Trigger выполнен либо явно указан блокер аккаунта; обновлён трекер.
- [ ] Проходят `npm run lint`, `npx tsc --noEmit`, `npm run build`.

## Официальные источники

[Повторы и обработка ошибок](https://trigger.dev/docs/errors-retrying) поддерживают ограничение попыток и отдельные повторяемые этапы.
