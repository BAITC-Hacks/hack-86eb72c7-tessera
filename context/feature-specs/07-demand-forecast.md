# 07 — Регулярный спрос: выбросы, отсутствие товара, сезонность и рост

## Цель и статус методики

Чистый детерминированный модуль `lib/domain/forecast/` формирует прогноз SKU/склада и объяснимые поправки. Это **предлагаемая базовая методика хакатона**, а не алгоритм из задания партнёра и не доказанный промышленный прогноз. Она должна удовлетворять M2–M4 и быть проверена в 15. Зависимости: 04, 05; UI/внешние модели не нужны.

## Контракт и конфигурация

`forecastDemand(dataset, scope, configuration) -> {series, evidence, warnings, coverage}`. Вход неизменяемый; дата расчёта `asOfDate`, историческое окно, источник сезонности/роста, пороги выбросов, параметры категории и политика неполных периодов хранятся в `lib/contracts/calculation.ts` и в запуске. Scope `{warehouseIds: string[], categoryIds: string[]}`: пустой массив = все доступные значения своего набора. Никакого чтения текущего времени внутри алгоритма. `runMode=full|diagnostic`: full требует источников всех обязательных возможностей (complete/explicit_none), diagnostic может вернуть неполную аналитику с `coverageGate=incomplete`, `blockingReasons` и `canApprove=false`. Если числовой прогноз не обоснован, возвращать unavailable, не выдумывать число.

Первоначальные проектные параметры (сохранить под `algorithmVersion`, подтвердить тестами): минимум 8 сопоставимых недель для выбросов; порог `median + 6 * 1.4826 * MAD` и одновременно `> 5 * median`; при нулевом MAD — второе условие с положительным минимумом единицы SKU. Нулевой/неизвестный baseline без достаточных наблюдений не даёт права автоматически исключить новый спрос. Все исключения сохраняют факты и причину. Порог «незначительного изменения» теста M4 — 5%, это наша измеримая интерпретация, не число из задания.

## Реализация по шагам

1. Отобрать только подтверждённые фактические продажи до конца `asOfDate`. Возвраты обрабатываются согласованной политикой источника, не через `abs()`. Не смешивать единицы, документы-заказы с отгрузками, транзакции с их месячными агрегатами. Пропуски не заполняются нулём без известной доступности наблюдений.
2. Объединить строки одного события `(source, documentId, sku, warehouse)` до поиска выброса. Дополнительно анализировать `(anonymousCustomerId, sku, warehouse, calendarWeek)` для продаж, разбитых на документы. Клиентские ID в доказательствах только внутренние псевдонимы, не в модели/общем UI.
3. Сравнивать событие и клиентскую неделю с сопоставимой историей до текущего события: та же сезонная часть года/доступные предыдущие циклы или предварительно нормализованная сезонность. Сезонный коэффициент для первичной очистки — медианная устойчивая оценка по предыдущим полным циклам либо подтверждённый внешний индекс; не подгонять его по проверяемому выбросу. Короткая история -> предупреждение, ручная проверка, без агрессивного удаления.
4. Исключать только аномальный избыток сверх сопоставимого baseline, не весь регулярный объём клиента. Регулярный крупный клиент и повторяющийся сезонный пик не исключаются лишь из-за размера. Перекрывающиеся документные/клиентские исключения объединять на уровне исходных строк, не вычитать дважды. Хранить `rawQty`, `excludedQty`, `regularQty`, метод и ссылки источников. Партнёрские данные без клиента получают `customerAnomalyCoverage=unavailable`, не подмену ID документом.
5. Объединить перекрывающиеся интервалы отсутствия `[start,end)`. Для каждого отсутствующего дня оценить недоступный спрос по медиане очищенных продаж сопоставимых доступных дней (тот же день недели/сезон, только история до среза). Поправка `max(0, comparableDemand - observedSales)` добавляется один раз. Сохранить исходный и восстановленный ряды, число дней, метод/качество. Если доступных сравнений нет — `insufficient_evidence`, не деление на ноль. Месячный нулевой остаток не является интервалом.
6. Для сезонной модели использовать полные месяцы с известной экспозицией. Предлагаемый baseline: не менее двух полных годовых циклов. В каждом году нормировать восстановленный месячный среднедневной спрос на годовой среднедневной; индекс месяца — медиана отношения по годам, затем нормировка среднего индекса к 1. Нулевые знаменатели/недостаток истории -> подтверждённый индекс категории или явный резервный несезонный режим с предупреждением. Общие денежные таблицы не считать индексом количества без подтверждения.
7. Десезонировать дневные/месячные значения. Устойчивый рост: сравнить медиану последних трёх полных месяцев с предыдущими тремя; включить положительный тренд только если не менее двух из трёх пар месяцев подтверждают рост. Отношение преобразовать в месячный множитель `pow(recent/prior, 1/3)`; ограничение максимума — явный параметр категории, не скрытая константа. Ноль в знаменателе/новый товар -> недостаток доказательств и согласованный резервный режим.
8. Зафиксировать календарную шкалу `u(date)=12*year+(month-1)+(day-1)/daysInMonth`. Якорь базы — середина среднего из последних трёх полных месяцев: `uAnchor=12*year+(month-1)+0.5`; `baseAnchor` — медиана трёх десезонированных среднедневных значений. `start=asOfDate+1 календарный день`. Рассчитанный месячный множитель `r` из шага7 переносит базу к первому дню: `baseAtStart=baseAnchor * r^(u(start)-uAnchor)`. Это явно выбранная аппроксимация, проверяемая отдельно, не факт о точности прогноза.
   Для будущего дня `d`: `delta=u(d)-u(start)`; `trendFactor=r^delta`, кроме replace, где он равен1; `externalGrowthFactor=g^delta` для replace/incremental, иначе1. `dailyForecast=baseAtStart * seasonalIndex(month(d)) * trendFactor * externalGrowthFactor`. Внешний рост меняет будущую траекторию, не повторно исторический перенос базы. Все H дней — от start до `asOfDate+H` включительно. Значения неотрицательны; промежуточные величины не округляются до шага заказа. `g` — подтверждённый положительный месячный множитель: например, годовой множитель переводится через степень1/12 только при явном годовом определении источника; проценты/множители не угадываются.
9. Внешний прирост имеет явную семантику: `growthMode=replace|incremental|none`. `replace` заменяет только будущий рассчитанный тренд (исторический перенос базы к start уже определён в шаге8); `incremental` применяется дополнительно **только** при подтверждении, что источник описывает отдельный прирост; `none` допустим лишь для явно отсутствующего/нулевого прогноза, не для потерянного источника. Сырые коэффициенты Systeme не интерпретировать без подтверждения.
10. Неполный текущий месяц по умолчанию не участвует в полномесячных индексах/тренде; используемые дневные факты остаются видимыми. Любой режим пересчёта экспозиции задан явно. Категории влияют через проверяемую политику горизонта/страховки/допустимого тренда, а не произвольную прибавку к спросу.

## Покрытие и ограничения

Готовый набор и возможность полного расчёта — разные вещи. Полный демонстрационный режим требует всех источников M1–M4; на неполных данных допускается явно неполная аналитика без утверждаемого заказа. Синтетический набор закрывает обязательные сценарии до получения данных партнёра. Не утверждать выполнение M3/M4 на реальных файлах без интервалов/клиента.

Не применять OpenAI для чисел, не подключать БД/Trigger/Liveblocks внутри чистой функции; не решать закупочную оптимизацию и MOQ.

## Проверка готовности

- [ ] Повтор входа даёт одинаковый результат; перестановка строк/разбиение события на строки его не меняет.
- [ ] Сезонный тест даёт больший прогноз в пике; устойчивый рост увеличивает прогноз, единичный всплеск — нет.
- [ ] Добавление события 100× baseline и его разбиение по документам одного клиента меняют регулярную потребность не более чем на 5%; повторяющийся крупный клиент сохраняется.
- [ ] При известном stockout и положительном сравнимом спросе прогноз выше сырых продаж; интервалы не дублируются; нет данных -> явная ошибка/неполнота.

- [ ] Внешний рост не учитывается дважды; неполный сентябрь/отрицательные коэффициенты/короткая история проверены.
- [ ] Есть тесты без утечки будущего и сравнительный отчёт с простым средним; качество не заявляется без измерений.
