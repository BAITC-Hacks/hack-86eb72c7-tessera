# Восстановление отправки Trigger.dev

`createCalculationRun` и `createImport` сохраняют операцию и `dispatch_intents` в одной транзакции PostgreSQL. HTTP возвращает `202` после коммита, не ожидая сетевого вызова Trigger. Необязательный post-response вызов `dispatchOne(pool, triggerTransport, type, id)` только ускоряет отправку; на него нельзя полагаться вместо восстановителя.

Отдельный процесс запускает `NODE_OPTIONS=--conditions=react-server npx tsx scripts/recover-dispatch.ts` периодически (например, раз в минуту) и при старте сервиса. Условие `react-server` необходимо для `server-only` вне Next.js; `trigger.config.ts` добавляет это же условие в сборку задач Trigger. Нужны серверные `DATABASE_URL`, `TRIGGER_SECRET_KEY`, `TRIGGER_PROJECT_REF`; параметры и учётная запись Trigger для реальной среды должны быть согласованы до запуска. Планировщик и мониторинг процесса — инфраструктурная обязанность развёртывания: без них восстановление после падения HTTP не гарантировано.

Восстановитель арендует до 25 готовых намерений через `FOR UPDATE SKIP LOCKED`, включая истёкшие аренды. Ключ Trigger всегда `calculation:{runId}` или `import:{importId}`, независимо от пользовательского ключа. Проверяются версия и хеш payload. После подтверждения сохраняется ID внешней задачи; только распознанные временные сбои повторяются с экспоненциальной задержкой 5–40 секунд, не более пяти попыток. SDK-вызов ограничен 15 секундами и одной внутренней попыткой, но уже отправленный ответ может прийти после локального тайм-аута — поэтому работник обязан повторно проверить БД. После окончательного отказа бизнес-операция переводится в `failed`, если ещё не завершена. Отказ и код ошибки безопасны для логов; исходные данные и секреты не пишутся. Окончательная бизнес-операция или архивированный проект не отправляются.

Для отменённых расчётов с уже отправленной задачей отдельный проход повторяет отмену Trigger по сохранённому ID. `cancel_attempts` и `cancel_ack_at` отделены от попыток отправки; после пяти безуспешных попыток остаётся код `cancel_unconfirmed` для операционного разбора, а бизнес-состояние `cancelled` остаётся главным и работник не должен публиковать результат. Вызов после гонки «отмена до подтверждения отправки» выполняется сразу и также остаётся восстановимым.

Ключ идемпотентности Trigger живёт один день; после его истечения повтор внешней задачи возможен. PostgreSQL и проверки внутри `trigger/calculate-procurement.ts` и `trigger/validate-import.ts` должны гарантировать один итоговый результат. Состояние `sent` означает только отправку, не успех расчёта/импорта. Параметры 600 секунд на задачу и три попытки вычисления — синтетические начальные ограничения; лимиты параллелизма задаются самими задачами. Это не согласованная промышленная политика. Проверка настоящего Trigger, учётной записи и региона требует инфраструктурных доступов; локальные тесты используют подменный транспорт.
