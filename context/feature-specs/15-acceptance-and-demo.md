# 15 — Приёмка кейса и воспроизводимая демонстрация

## Цель

Проверить пять обязательных требований и ограничения партнёра, подготовить русскую README и сценарий демонстрации. Зависимости: 14a и все предшествующие обязательные этапы. План/моки не считаются реализованным продуктом.

## Реализация

1. `tests/fixtures/` и `scripts/generate-demo-data.ts`: воспроизводимый синтетический набор с заданным seed, минимум двумя годовыми сезонными циклами, стабильным ростом, явными периодами недоступности, разовым крупным клиентом/дроблением по документам, двумя поставщиками, несколькими складами/категориями, запасами и разными ETA. Синтетическое происхождение явно в manifest/UI/отчёте.
2. `tests/domain/`: эталоны07/08; независимо менять каждый источник на ненасыщенной фикстуре. Сравнить с простым средним на отложенных периодах; фиксировать ошибку и ограничения, не только красивый график. Деление на ноль и нет наблюдений — отдельные случаи, не искусственная «100% точность».
3. `tests/integration/`: изоляция двух Clerk-пользователей; повторы импорта/run; сбои после записи БД до Trigger-dispatch; отмена во время ИИ; неверный/поддельный callback; пропущенные события realtime; конфликт review/approve; истёкшая ссылка S3; формульная инъекция CSV.
4. `tests/e2e/`: русский интерфейс, клавиатура, импорт → отчёт → run → supplier groups → rationale → edit → approve → export → refresh. Второй пользователь не получает файлы/комнату/результат первого.
5. README репозитория: назначение, стек и окружение, настройка Clerk/PostgreSQL/S3/Trigger/OpenAI/Liveblocks без секретов, миграции, запуск приложения и фоновых задач, импорт, синтетика, формулы/выбросы/stockout/рост, тесты, сборка/развёртывание, демонстрация, ограничения данных/1С. Указать точные проверенные версии пакетов после реализации.
6. Составить `context/acceptance-report.md`: требования → команды/фикстуры → результат, отдельно синтетика, данные партнёра, интеграции и формат1С. Не копировать конфиденциальные архивы в публичный репозиторий.

## Матрица приёмки

| Код | Проверка |
| --- | --- |
| M1 | Продажи, остатки, путь, категория, прирост и сроки действительно влияют на компоненты и итог специально выбранной фикстуры |
| M2 | Пик/спад воспроизводят сезонный паттерн; устойчивый рост повышает прогноз относительно плоского ряда |
| M3 | Известный stockout с сопоставимым спросом повышает unconstrained-потребность против сырых продаж |
| M4 | Одиночный заказ100× и разбитый заказ одного клиента не увеличивают регулярный спрос более проектного порога5%; регулярный крупный клиент не удалён |
| M5 | Каждая строка имеет поставщика/количество/срочность/числовую причину; видны группы поставщиков |
| Безопасность | Нет автоматического send/approve; нет идентифицирующих клиентских данных в расчёте/модели/логах; изоляция проходит |
| Надёжность | Повторы/отмена/частичный сбой не создают дубли или ложный успех; ИИ/realtime необязательны для числовой корректности |
| Совместимость | CSV проверен на согласованном образце1С либо совместимость честно остаётся неподтверждённой |

## Ограничения и готовность

Не добавлять новые функции под видом приёмки и не подменять отсутствующие реальные поля синтетикой без маркировки.

- [ ] Все M1–M5 проходят на фиксированных входах; результаты воспроизводимы другим участником.
- [ ] Настроенные сервисы прошли тестовую проверку либо ограничение перечислено; мок не считается реальной интеграцией.
- [ ] Отсутствующие в архивах клиентские ID/stockouts/lead time и ошибки Excel отражены в отчёте.
- [ ] README на русском позволяет воспроизвести запуск; секретов/закрытых данных в репозитории нет.
- [ ] Полный набор тестов, `npm run lint`, `npx tsc --noEmit`, `npm run build` проходят.
- [ ] Трекер отражает фактическую готовность и нерешённые партнёрские вопросы.
