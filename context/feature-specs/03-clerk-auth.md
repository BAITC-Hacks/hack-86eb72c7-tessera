# 03 — Аутентификация Clerk

## Цель

Дизайн-система и оболочка редактора существуют. Подключить Clerk и общие серверные функции получения личности; проекты, фоновые задачи и совместную работу пока не создавать.

**Статус:** запланировано, не реализовано. **Зависимость:** 02-editor.

## Перед началом

Прочитать шесть контекстных файлов и локальные руководства Next.js по Proxy/App Router. Clerk выбран пользователем, но не установлен. Подобрать стабильную версию `@clerk/nextjs`, совместимую с установленными Next.js 16.3.6 и React 19.2.8; зафиксировать в lock-файле и проверить её документацию. Не выдумывать ключи или настройки аккаунта.

## Реализация

1. Установить `@clerk/nextjs`; добавить `ClerkProvider` в `app/layout.tsx`, сохранив тёмную тему, шрифты и сгенерированные примитивы. Установить `html lang="ru"` и русские metadata приложения. Локализовать пользовательские тексты Clerk на русский поддерживаемым выбранной версией способом; если нужен пакет локализаций, согласовать и зафиксировать его версию.
2. Создать корневой `proxy.ts` с `clerkMiddleware` и официальным matcher для страниц/API без статических ресурсов. Это контекст сессии, а не достаточная защита данных. Не копировать устаревающий `createRouteMatcher` из старых руководств.
3. Создать `app/sign-in/[[...sign-in]]/page.tsx` и `app/sign-up/[[...sign-up]]/page.tsx` с компонентами Clerk и токенами темы. Возврат после входа — только на разрешённый локальный путь; демонстрационная `/workspace` появится в12, реальное подключение — в13. До её появления не оставлять сломанный редирект: временный адрес `/` явно документировать.
4. Создать серверную `lib/server/auth.ts` с `requireUserId()`, использующей ожидаемый через `await` серверный `auth()`. Не доверять ID из JSON, строки запроса или localStorage. API преобразуют отсутствие сессии в общий JSON `401`, не в HTML-редирект.
5. Добавить `lib/contracts/api.ts` с форматом ответа из архитектуры, если его ещё нет; последующие спецификации переиспользуют его.
6. Добавить в `.env.example` только названия/безопасные заглушки: `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`, адреса входа/регистрации. Проверять обязательную конфигурацию на сервере; отсутствие ключей — недоступная конфигурация, не фиктивный пользователь.
7. Проверить вход/выход/истечение сессии узким тестовым сценарием. Не реализовывать рабочую область в03 ради демонстрации: макет относится к12, подключение — к13; меню пользователя подключается там же.

## Правила доступа

- Публичные пути: `/`, `/sign-in`, `/sign-up`, необходимые ресурсы Clerk/статика. Будущие `/workspace` и приватные API проверяют доступ непосредственно у ресурса.
- `requireUserId()` устанавливает личность, не владение. Проверки проекта добавляются в 06 и обязательны для импорта, расчёта, экспорта и комнаты.
- Первая версия: один владелец проекта. Без Clerk Organizations, приглашений, общего редактирования и административных ролей.
- Пользовательские мутации с cookie-сессией отклоняют запросы с чужого origin по единой политике приложения. UI входа не заменяет эту защиту.
- `CLERK_SECRET_KEY` доступен только серверу; публичный ключ не даёт права на данные.

## Ограничения объёма

Не добавлять таблицы БД, webhooks, CRUD проектов, клиенты Trigger/OpenAI/Liveblocks и закупочный интерфейс. Не менять `components/ui/*`. Не объявлять будущие API защищёнными до проверки владельца.

## Проверка готовности

- [ ] Подстановка ID не позволяет выдать себя за другого пользователя; серверный ключ отсутствует в браузерном коде/логах.
- [ ] Экран входа русский, тёмный, доступен с клавиатуры; нет цикла редиректов и внешнего return URL.
