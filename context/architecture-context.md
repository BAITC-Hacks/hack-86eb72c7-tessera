## Границы системы

- `app/`: страницы и обработчики запросов; валидация, идентификация, проверка доступа, вызов сервисов. Не разбирать целую книгу и не строить прогноз внутри HTTP-запроса.
- `components/editor/`, `components/procurement/`: оболочка и представление закупок; без серверных секретов и прямой записи в БД.
- `lib/contracts/`: проверяемые во время выполнения DTO, статусы и формат ошибок.
- `lib/server/`: авторизация, БД, приватные объекты, импорт, запуски, утверждение и экспорт; только сервер.
- `lib/domain/`: чистые функции нормализации, прогнозирования и пополнения без сетевых зависимостей.
- Общая сумма дневного прогноза принадлежит07: `sumDailyForecast(model, from, to)` сохраняет числовой API, а перегрузка с четвёртым аргументом `"decimal"` возвращает каноническую строку numeric(30,8) для08. Обе используют один вычислитель;08 не копирует формулу и не переводит точные количества в `Number`. Числовое представление остаётся приближённым на больших величинах; денежные/количественные DTO используют десятичную перегрузку.
- `lib/ai/`: минимизированный контекст объяснения, проверка ответа, шаблонный резервный вариант, версии промптов; только сервер.
- `lib/realtime/`: выдача ограниченного доступа Liveblocks и публикация обезличенных событий; запись только сервером.
- `trigger/`: оркестрация фоновых этапов через доменные сервисы, без копирования формул.
- `tests/`: детерминированные наборы, проверки доступа, интеграции и приёмка обязательных требований.

Это целевые границы. Конкретные файлы задаются спецификациями; заранее создавать пустые модули не нужно.

## Модель хранения

PostgreSQL — источник истины для следующих сущностей:

- `Project`: рабочая область закупщика с владельцем `ownerUserId` из Clerk. В первой версии нет совместного редактирования и членства в организациях.
- `Import`, неизменяемая `DatasetVersion`: контрольная сумма, сопоставление полей, результаты проверки, происхождение, дата среза и доступность источников. Новый импорт создаёт новую версию, не переписывая входы старого расчёта.
- Версионные товары, категории, поставщики/сроки поставки, склады, продажи, остатки, товары в пути, stockout-интервалы и прогноз прироста. Анонимный ключ клиента используется только внутри защищённого расчётного контура.
- `CalculationRun`: версия входов, область расчёта, снимок/хеш параметров, версия алгоритма, статус/этап, монотонная `stateVersion`, ссылка на выполнение, безопасная ошибка и время.
- Сохраняемое намерение dispatch: тип `import | calculation`, ID бизнес-операции, ключ идемпотентности, версия payload, попытки отправки, ID внешней задачи и безопасная ошибка. Создаётся транзакционно с операцией; восстанавливается после сбоя. Статус отправки не заменяет бизнес-статус.
- Попытка импорта фиксирует `manifestHash`, версии адаптера/схемы и `stateVersion`. Исправленный manifest того же файла создаёт новую попытку; дедупликация только по checksum файла не должна подавлять новую версию данных.
- `Recommendation`: неизменяемое рассчитанное количество, поставщик, числовые факторы, срочность и детерминированное обоснование.
- Корректировки менеджера, `reviewVersion`, `Approval`, `ExportArtifact`, аудит: изменения отделены от исходного результата; фиксируются автор, время, причина и точная утверждённая ревизия.
- Необязательное ИИ-объяснение и события запуска: версии модели/промпта/схемы, ссылки на доказательства, признаки деградации; без записи скрытого процесса рассуждений.

Приватное S3 хранит исходные таблицы и экспорт; БД — ключи объектов, владельцев, контрольные суммы и происхождение. Публичные ссылки и сырые файлы в Liveblocks запрещены. Политика удаления должна охватывать БД, S3, логи задач и данные у поставщиков; реальные данные партнёра нельзя отправлять во внешние сервисы до согласования политики.

## Поток обработки

1. Clerk подтверждает личность; сервер находит проект, принадлежащий пользователю.
2. Отдельная задача `validate-import` из 09a проверяет приватные источники и атомарно публикует неизменяемую версию данных. Импорт не является `CalculationRun`; состояния, отчёт и dispatch у него отдельные. Отсутствующее поле не приравнивается к нулю.
3. Авторизованный запрос фиксирует версии данных/параметров/алгоритма и создаёт уникальный запуск со статусом `queued` и сохраняемым намерением отправки задачи.
4. Trigger.dev выполняет **validate → forecast → recommend → explain**. Первые три этапа — детерминированный код, не LLM. Генеративный этап `explain` допускает замену шаблонным текстом.
5. Изменение состояния сначала записывается в БД, затем публикуется в Liveblocks по возможности. Повторное чтение/опрос восстанавливает актуальное состояние после разрыва связи.
6. Менеджер проверяет сгруппированные по поставщикам рекомендации, сохраняет корректировки и явно утверждает конкретную `reviewVersion`.
7. Авторизованный экспорт использует именно утверждённый снимок. Задача, модель, событие комнаты и браузерное состояние не могут утвердить или отправить заказ.

## Доступ, контракты и ошибки

- Каждый приватный запрос получает Clerk ID на сервере и проверяет владельца проекта через цепочку связанных ресурсов. Нет сессии — `401`; ресурс отсутствует или принадлежит другому — `404`. ID пользователя из тела запроса не принимается.
- JSON API: `{ data: ... }` и `{ error: { code, message, requestId, details? } }`. Ответ токена Liveblocks и скачивание файла — явные исключения формата.
- `CalculationRun.status`: `queued | running | succeeded | failed | cancelled`; этап: `validate | forecast | recommend | explain`; состояние этапа: `pending | running | succeeded | failed | skipped`.
- Сбой ИИ даёт признак ухудшения объяснения, но не превращает корректный числовой расчёт в ошибку. Успешный расчёт не означает утверждение заказа. `runMode=full/diagnostic`, `coverageGate=complete/incomplete`, `blockingReasons` и серверный `canApprove` определяют полноту; diagnostic с пробелами никогда не утверждается.
- Безопасные повторы обеспечиваются уникальностью записей и проверкой переходов БД вместе с идемпотентностью Trigger. Намеренный новый расчёт создаёт новый запуск; повтор не переписывает исходные результаты.
- Комната Liveblocks: `project:{projectId}:run:{runId}`. Сервер проверяет принадлежность идентификаторов; разрешения с `*` на комнаты запрещены. Событие только уведомляет о необходимости повторного чтения, но не выполняет команду.
- Логи содержат безопасные коды ошибок, число попыток и время; не содержат таблицы, ключи клиентов, секреты и полные промпты. До включения внешних вызовов задаются конечные ограничения времени, параллелизма, токенов и бюджета.

## Инварианты

1. Расчёт учитывает все переданные обязательные источники: товары в пути, категории/прирост, сезонность, устойчивый тренд, stockout и разовые/клиентские выбросы.
2. Одинаковые входы/параметры/версия алгоритма дают одинаковые числовые рекомендации; LLM не может менять количество.
3. Необезличенные клиентские данные отклоняются. Анонимный ключ доступен детектору выбросов, но не отправляется в OpenAI.
4. Для каждой строки доступны числовые факторы и шаблонное обоснование даже при отказе OpenAI/Liveblocks.
5. Утверждение и экспорт проверяются сервером относительно ревизии. Автоматической отправки поставщику в первой версии нет.
6. Бизнес-статус и аудит определяет БД, а не интерфейсы Liveblocks/Trigger или локальное состояние.
7. Серверные ключи закрыты; нет доступа к чужим файлам, результатам, задачам и комнатам или общего кеша приватных данных.
8. Пробелы в источниках показываются явно: в текущих данных нет подтверждённых клиентских ID/цен в динамике, явных stockout-интервалов и справочника сроков; ошибочные Excel-ячейки не считаются нулями. Конкретные блокировки/предупреждения определяют спецификации импорта и расчёта.

## Решения этапа05 (в работе)

- Импорт — серверный сервис/локальный CLI, без тяжёлого HTTP и оркестрации09a. ZIP проверяется yauzl, XML — fast-xml-parser; числа/ошибки/кеш формул сохраняются явно, формулы не вычисляются.
- Исходные ZIP партнёра в данном checkout отсутствуют: лимиты синтетической проверки не подтверждают приём всех12 реальных книг. Базовый предел исходного объекта04 остаётся25MiB; дополнительные ограничения распаковки фиксируются парсером.
- Расширенный manifest05 должен хранить и хешировать семантику, периоды, единицы, приоритеты и основания коррекций; совместимое расширение JSON-контракта04 не изменяет старые снимки.
- Общие package/lock остаются у B по разделению работ; точные зависимости передаются в scripts/data-import-dependencies.json вместе с зависимостями04.

## Решения этапа06 (в работе)

- HTTP только готовит приватную загрузку и сохраняет manifest; парсер05 не вызывается. До09a нет фонового dispatch, finalize возвращает awaiting-validation/validationPending.
- Первичная загрузка создаёт предварительную попытку без окончательного manifest; при необходимости аддитивная миграция разрешает ровно однократную фиксацию только такого manifest, не ослабляя неизменность прежних/исправленных попыток. Старые миграции не редактируются.
- Лимиты: источник25MiB, подпись до300с; активные загрузки ограничиваются транзакционно, HTTP rate-limit процесса — ограничение хакатонной версии, не распределённая квота. Закрытость bucket/HEAD проверяются серверным адаптером, ETag не считается SHA256.
