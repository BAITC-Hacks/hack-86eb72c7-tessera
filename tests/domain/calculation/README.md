## Исправления после объединения main `3ea1770`, 23.09.2026

Первый прогон выявил конфликтное объединение loader (SyntaxError) и отсутствие обязательной `growthSemanticsByAssumption: []` в старой фикстуре08. После исправления тестовой инфраструктуры прошли126/129 проверок, включая все110 прежних тестов. Три новые регрессии выявили два дефекта интеграции:

1. **Исключение вместо недоступной строки.** При отсутствующей семантике роста или неподтверждённом независимом приросте07 возвращает неполный прогноз, эффективный `growthMode=none` и блокирующее предупреждение.08 теперь допускает этот строго ограниченный случай и возвращает `quantityStatus=unavailable`, `recommendedQty=null`, `canApprove=false`. Добавлены проверки отсутствующего источника, full/diagnostic, глобального предупреждения и негативные контроли: чужой SKU/склад, неблокирующее/отсутствующее предупреждение, полное покрытие, другой ненейтральный режим и будущая дата по-прежнему не позволяют обойти проверку.
2. **Дублированная формула и несовместимая точность.**08 теперь вызывает единую функцию07 с перегрузкой `"decimal"`. BigInt-суммирование сохраняет большие количества и дроби; календарная разность не вычитает близкие большие дробные числа. Публичный трёхаргументный API по-прежнему возвращает `number`.

Регрессия большой суммы уточнена: прежнее преобразование `number.toFixed(8)` не может сохранить все8 знаков при величине около10⁹. Теперь тест строго сравнивает десятичный API07 с DTO08 и независимо закрепляет эталон **`1027882215.44612681`**; числовая проекция также проверяется. Это не допуск погрешности и не пропуск теста. Отдельно проверены точное большое количество `9007199254740993`, малая дробь рядом с ним, накопление подточных дневных значений и half-up после суммирования. Дробные степени по-прежнему приближённые (`Math.pow`), произвольная математическая точность не заявляется.
