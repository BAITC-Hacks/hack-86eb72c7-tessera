# 08 — Расчёт рекомендуемого заказа

## Цель

Чистый модуль `lib/domain/replenishment/` превращает прогноз 07 и все обязательные источники в рекомендации по поставщикам с числовым обоснованием. Основание: M1/M5 и выход §5 задания. Зависимость: 07.

## Контракт

`calculateRecommendations(forecast, inventory, inbound, supplierTerms, categoryPolicies, configuration)` возвращает строки `{productId, supplierId, warehouseId, supplierArticle, unit, recommendedQty, quantityStatus, urgency, evidence, warnings}`. Известные количества — десятичные строки на внешней границе; при diagnostic и недостатке доказательств `recommendedQty=null`, `quantityStatus=unavailable`; иначе `quantityStatus=known`. Null никогда не означает ноль и не проходит утверждение/экспорт. Ошибки/пробелы отдельно; нельзя молча исключить SKU. Для каждой строки есть `calculationVersion`, `datasetVersionId` и ссылки фактов.

`configuration` расширяет общую схему 07: `asOfDate`, `reviewPeriodDays`, `safetyDaysByCategory`, `leadTimePolicyVersion`, `unitPolicyVersion`, `growthMode`, `seasonalityMode`, `algorithmVersion`; все диапазоны/перечни проверяются. Сроки — целые неотрицательные календарные дни начальной версии, но согласование календаря с партнёром обязательно. Нельзя выводить норматив lead time из ETA конкретной партии.

## Реализация расчёта — предлагаемая методика

1. Для SKU/склада определить одного подтверждённого поставщика. Неоднозначность — блокирующее предупреждение, без автоматического выбора «лучшего».
2. Горизонт `H = leadTimeDays + reviewPeriodDays`. Политика категории задаёт `safetyDays`, влияя на результат, а не только на отображение. Все параметры имеют источник/версию; категория без политики не получает незаметный ноль.
3. `usableStock` = подтверждённый свободный остаток **или** `onHand - reserved`, не оба одновременно. Отрицательный пригодный остаток запрещён/требует разрешённой политики задолженности; первоначально блокировать строку. Месячный начальный остаток не выдавать за текущий.
4. `eligibleInbound` — подтверждённые неотменённые количества той же единицы/SKU/склада с ETA в `(asOfDate, asOfDate + H]`. Просроченные, без даты или поздние партии показываются отдельно; не списывать их молча и не уменьшать ими потребность. Дубли поставок между файлами не суммируются. Срез остатков — конец asOfDate; поступления того же дня уже входят в остаток и повторно не вычитаются. В будущем дне приход учитывается перед дневным спросом; это проектная календарная конвенция, фиксируемая в конфигурации.
5. `forecastDemandH` — сумма дневного прогноза на H. `safetyStock` — сумма прогноза на следующие `safetyDays` после H. `rawNeed = max(0, forecastDemandH + safetyStock - usableStock - eligibleInbound)`.
6. Начальная версия округляет положительный `rawNeed` вверх до подтверждённого минимального шага единицы SKU. Дробные метры/единицы допустимы при заданной точности; ноль остаётся нулём. MOQ/кратность пока только метаданные, не применяются: это опция задания, отдельная будущая спецификация.
7. Моделировать дневной остаток с учётом дат поступлений для срочности. `unknown` — недостаточно данных, строка не утверждается; иначе `urgent` имеет приоритет при прогнозируемом дефиците до первой возможной новой поставки **даже при нулевом rawNeed**; иначе `planned` — положительный заказ; иначе `none`. Дополнительно сохранять `projectedStockoutDate` и число дефицитных дней. Это проектные значения, русские подписи в UI. Поставка в конце горизонта может уменьшать количество, но не скрывает ранний дефицит.
8. Группировать по поставщику, внутри сохранять склад/SKU. Не суммировать количества разных единиц в «общий объём». Нулевые рекомендации доступны в фильтре, не становятся строками экспортируемого заказа.
9. `evidence`: база, сезонность, рассчитанный/внешний рост, компенсация stockout, исключённый объём, горизонт/страховка, onHand/reserved/usableStock, учтённые/неучтённые партии, rawNeed, округление, финальное количество, качество/источники. Формировать русское шаблонное объяснение для **каждой** строки до вызова ИИ.

## Ограничения

Не создавать API, UI, утверждение или отправку; не изменять импортированные значения. OpenAI может переформулировать факты позже, но не вычислять заказ. Неполная аналитика имеет `coverageGate=incomplete`, `blockingReasons`, `canApprove=false` по04/07. Строки без обоснованного количества помечаются unavailable, не нулевыми. Ручной ввод недостающих предпосылок допускается только как явно подтверждённая новая версия конфигурации/набора.

## Проверка готовности

- [ ] Точный эталон: прогноз горизонта 100, страховка 20, свободный остаток 30, подходящий путь 40 -> потребность 50 до округления.
- [ ] Каждая обязательная группа входов M1 меняет свой вклад и ожидаемый итог на ненасыщенной фикстуре: продажи, stock, inbound, категория/политика, рост; также lead time.
- [ ] Не требовать изменения округлённого итога при любом малом изменении: нулевой порог/округление законно скрывают часть разницы.
- [ ] ETA на asOfDate, первом дне и последнем дне H не учитывается дважды; тест нулевого rawNeed с ранним дефицитом сохраняет urgent.
- [ ] Поздняя/неизвестная поставка не уменьшает количество; ранний дефицит виден; резерв не вычитается дважды.
- [ ] Смешанные единицы, неоднозначные поставщики, пропуски и отрицательные значения дают явные ошибки.
- [ ] Каждая строка имеет поставщика, количество, объяснение, срочность; ИИ отключён — всё это сохраняется.
- [ ] Тесты, `npm run lint`, `npx tsc --noEmit`, `npm run build` проходят.
