# Правила работы ИИ-разработчика

## Источники и подход

Работать по кейсу `techtask/TECHTASK.md`, последовательно прочитав шесть файлов из AGENTS.md и полную активную спецификацию. `architecture-context.md` — основной документ; `architecture.md` — совместимая ссылка. Этапы 01/02 — завершённая история, не переписывать их функциональный объём задним числом.

Приоритет: явные решения пользователя и ограничения партнёра → инварианты контекста → активная спецификация. Конфликт сообщать, не разрешать молча. Разделять подтверждённое требование, наблюдение в коде/данных, предложенное решение и неизвестное. План не доказывает наличие реализации. Интерфейс и документация — на русском.

## Границы работы

- Одна проверяемая единица за раз. До изменения отмечать начало, после значимых изменений обновлять `progress-tracker.md`.
- Соблюдать зависимости `feature-specs/00-build-plan.md`. Независимые макеты UI могут выполняться раньше подключений.
- Разделять математику, API, фоновые задачи, макеты и интеграции. Не добавлять соседние возможности «на будущее».
- Запрещены автономная отправка поставщику, расчёты с идентифицирующими клиентскими данными, скрытые значения по умолчанию и количества, придуманные моделью.
- Пакеты устанавливать только в ответственном этапе; сначала проверить официальную документацию провайдера и локальные инструкции Next.js.
- Субагентов запускать по запросу пользователя или явному требованию процесса. Разделять файлы/контракты, предупреждать о параллельных изменениях; ведущий повторно проверяет результат. Не запускать и не восстанавливать tmux Team неявно.

## Неопределённости

Неизвестную бизнес-семантику записать в вопросы и уточнить до реализации зависимого поведения. Продолжать независимую работу. Не выдумывать сроки поставки, коэффициенты, единицы, связи поставщиков, формат 1С, интервалы отсутствия товара и гарантии обезличивания.

Предложенные параметры явно помечены и версионируются. Синтетические данные допустимы, но не являются данными партнёра и доказательством полноты его выгрузки. PostgreSQL и S3 выбраны пользователем; конкретные провайдеры, ORM, сроки хранения и бюджет ещё требуют решения. Ссылка на документацию не доказывает доступность аккаунта/тарифа или разрешение на передачу данных.

## Порядок выполнения

1. Прочитать требования, зависимости, ограничения и критерии приёмки.
2. Отметить активный этап и блокирующие вопросы в трекере.
3. Определить контракты/фикстуры; сохранить происхождение данных и ожидаемые вычисления.
4. Реализовать минимальный объём. При согласованном изменении архитектуры, хранения или числовой политики сначала обновить контекст.
5. Выполнить предметные тесты и проверки типов/линтера/сборки. Связать требования с конкретными тестами; указать ограничения внешней среды.
6. Повторно проверить права, приватность, повторы, гонки и устаревшие утверждения, не только успешный путь.
7. Записать доказательства завершения, пробелы и следующий этап. Успешной компиляции недостаточно для функциональной готовности.

## Защищённые материалы

Не менять `techtask/*`, сгенерированные `components/ui/*`, сторонние библиотеки, функциональные требования завершённых этапов, пользовательские изменения и чужое состояние выполнения без отдельного указания. Перевод завершённой спецификации не меняет её приёмку. Не коммитить/отправлять код или архивы партнёра и не удалять данные в рамках документационной задачи. `/context` уже исключён из Git: сообщать об этом, не менять `.gitignore` молча.

## Завершение

Для кода: предметные проверки + `npm run lint` + `npx tsc --noEmit` + `npm run build`. Для итоговой поставки: M1–M5, демонстрация проверки/утверждения/экспорта, честное описание неполных реальных данных и согласования 1С, README с методологией, алгоритмом выбросов и запуском. Для документации: покрытие источников, порядок зависимостей, согласованные контракты, существующие ссылки и явные нерешённые вопросы.
