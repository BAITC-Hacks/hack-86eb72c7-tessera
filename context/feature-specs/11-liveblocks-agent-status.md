# 11 — Активность агентов через Liveblocks

## Цель

Фоновый расчёт и его статусы уже сохраняются в БД. Подключить Liveblocks для показа выполняемого этапа и присутствия агента. Источник истины остаётся PostgreSQL; жизненным циклом задач управляет Trigger.dev.

**Статус:** независимые адаптеры приняты по исходникам и13 mock-тестам; маршрут с проверкой владельца в БД, публикация из задач и живой smoke ещё не подключены. **Зависимости:** 03, 06, 09. Проверка владельца проекта использует 06. UI-компоненты описаны в 12; подключение их к этому транспорту — в 13. Фактические интерфейсы и ограничения — в [b-handoff.md](../b-handoff.md).

## До реализации

Проверить совместимые текущие версии `@liveblocks/node`, `@liveblocks/client`, `@liveblocks/react`, зафиксировать версии. `LIVEBLOCKS_SECRET_KEY` доступен только серверу. Аккаунт, регион, ограничения запросов/комнат и политика хранения согласуются отдельно. Нет ключей — показывается обычный опрос API, а не фиктивно работающий realtime.

## Контракты

- Комната: `project:{projectId}:run:{runId}`. Только сервер создаёт приватную комнату без публичного доступа. Проверять, что запуск относится к проекту и проект принадлежит текущему Clerk-пользователю.
- `POST /api/liveblocks-auth` принимает `{ room }`, где `room` разбирается по строгому формату. Клиентский ID пользователя не принимается. Сервер использует Clerk ID и выдаёт разрешение чтения только точной проверенной комнаты; никаких wildcard-комнат и полного доступа на запись.
- Успех — нативный ответ токена Liveblocks, а не `{ data }`, потому что его потребляет SDK; ошибки — общий формат: `401` без сессии, `404` чужая/неизвестная комната, `422` неверная форма, `503` недоступный поставщик.
- Уведомление: `{ type: "run.updated", projectId, runId, stateVersion, stage, status, emittedAt }`. Это сигнал перечитать `GET /api/runs/[runId]`, а не доверенный результат вычисления. Порядок определяет `stateVersion`, не клиентское время.
- Серверное присутствие: `agent:{runId}:{stage}`, данные `{ runId, stage, status }`, русское имя этапа. Срок жизни ограничен и обновляется только во время реальной работы. Исчезновение presence не означает завершение/ошибку бизнес-запуска.

## Реализация

1. `lib/realtime/server.ts`: серверный клиент, создание/поиск приватной комнаты, функции публикации. Не экспортировать секреты в общие клиентские модули.
2. `app/api/liveblocks-auth/route.ts`: авторизация сессии и владельца в БД при каждой выдаче токена, затем `prepareSession`/разрешение чтения/`authorize` по установленной версии SDK. Клиент не может создать или авторизовать комнату произвольной строкой.
3. `lib/realtime/publish-run-status.ts`: после коммита версии состояния вызвать серверный `broadcastEvent`; для текущего этапа использовать `setPresence` с конечным TTL. Запись статуса в БД остаётся обязательной даже при сбое Liveblocks; публикация ограничена по времени/частоте.
4. `lib/realtime/contracts.ts`: DTO уведомления/presence, проверка размеров, перечисления этапов. Не включать продажи, клиента, промпты, таблицы, рекомендации целиком, подписанные ссылки и stack trace.
5. `components/providers/run-room-provider.tsx`: узкий клиентский провайдер комнаты, без переработки UI. Подписка только активного авторизованного запуска; смена проекта/выход очищают подписку. Реальную страницу подключает 13.
6. `hooks/use-run-status.ts`: стартовать с серверного снимка БД; по уведомлению перечитать API; отбрасывать старые версии. Перечитывать при reconnect и фокусе окна; при недоступности realtime использовать ограниченный опрос с backoff, останавливаясь в конечном состоянии/после размонтирования. Численные интервалы задать и проверить при реализации относительно лимитов аккаунта.
7. Тестовый клиентский сценарий проверяет обновления в двух сессиях владельца. Посторонняя сессия не должна получить ни токен, ни данные комнаты. Историю событий при необходимости читать из БД, не создавать второй источник аудита в Liveblocks.

## Безопасность и честность интерфейса

- В MVP разрешение на чтение комнаты достаточно: пользовательская совместная запись и presence пользователей не требуются. Нельзя расширять доступ ради удобства примера из документации.
- События браузера не имеют силы для расчёта, отмены или утверждения. Даже поддельный `succeeded` только вызывает проверенное чтение БД; не разблокирует утверждение сам по себе.
- Этапы проверки/прогноза/рекомендаций подписаны как детерминированные, объяснение — как ИИ. Не изображать несколько автономных LLM-агентов, когда работает обычный код.
- При разрыве связи русское состояние «Обновления задерживаются»; показывать время последнего подтверждённого снимка. Не бесконечный индикатор без возможности восстановить данные.
- Уже выданный токен может действовать до истечения; не обещать мгновенное снятие доступа только выходом в UI. Механизм отзыва/срок токенов проверить в выбранной версии и согласовать до добавления шаринга. Первоначальная модель владельца не меняется через Liveblocks.

## Ограничения объёма

Не делать Liveblocks БД заказов, планировщиком агентов или каналом команд. Не внедрять общий редактор, Comments, AI Chat, Liveblocks Storage для расчётов либо параллельный постоянный журнал активности. Не добавлять approval и не менять детерминированное ядро.

## Проверка готовности

- [ ] Владелец получает доступ только к точной комнате своего запуска; без сессии `401`, другой пользователь `404`.
- [ ] Подстановка project/run/room ID, wildcard и клиентская запись статуса не дают доступ/влияние на бизнес-состояние.
- [ ] После отказа Liveblocks, потери/перестановки событий, reconnect и обновления страницы UI восстанавливает состояние БД.
- [ ] Публикация не меняет результат задачи; presence исчезает по TTL, но результат остаётся доступен.
- [ ] Есть реальный smoke-тест аккаунта либо честный блокер; секреты и исходные данные не передаются клиенту/в комнату.
- [ ] Подписки/таймеры очищаются при выходе и смене проекта; обновлён трекер.
- [ ] Проходят `npm run lint`, `npx tsc --noEmit`, `npm run build`.

## Официальные источники и оговорки

Проверены 23.09.2026: [агенты Liveblocks](https://liveblocks.io/docs/use-cases/agentic-users) поддерживают присутствие и активность; [Node API](https://liveblocks.io/docs/api-reference/liveblocks-node) описывает `setPresence` с TTL и `broadcastEvent`; [access tokens](https://liveblocks.io/docs/api-reference/authentication/access-token) позволяют серверу задавать доступ к комнатам. Документация предпочитает ID tokens для сложных вложенных организаций/групп; выбранный здесь ограниченный access-token сценарий относится только к одному владельцу и точной комнате. При расширении модели доступа нужен отдельный пересмотр, не автоматическое добавление wildcard.
